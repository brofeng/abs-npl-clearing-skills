实际做单时 70% 的时间花在**上游取数**——从 681 页说明书、N 份受托报告、

## 〇、3.0 相对 2.0 改了什么（先看这段）

2.0 的语义断言里**硬编码了惠元 2021 年第三期的数值**（`0.9114065`、`99.18%`、
`5,763,476.69`、`2.28/3.04/4.14/4.89/5.48`），所以它只对那一单成立，换一单必然 FAIL。
3.0 把这些全部改为由 payload / metrics 驱动，**同一套门禁可直接用于任意清算期不良ABS**。

在中信银行 15 单实操中，2.0 的门禁**放过**了三类真实错误：

| 单 | 2.0 判定 | 实际情况 | 3.0 靠哪条抓住 |
|---|---|---|---|
| 2022 年第四期 | ✅ 113/113 | 优先档逐期本金多算 **6,910 万**，次级 XIRR 虚高 **218%** | 逐期分档本金合计 ＝ 清算兑付额；XIRR 合理区间 |
| 2022 年第六期 | ✅ 通过 | 漏「受托机构报酬」**25 万** | 费用明细合计 ＝ 披露合计 |
| 2023 年第七期 | ✅ 通过 | 同上，漏 25 万 | 同上 |

**根因不是"断言写少了"，而是只做了"自洽检查"**：校验了清算报告一侧的数字对不对，
没校验"逐期加总"与"清算报告"是否一致；校验了科目名称在不在，没校验"明细合计"与"披露合计"
是否对平。两个都自洽，但互相对不上，门禁就看不见。

| 维度 | 2.0 | 3.0 |
|---|---|---|
| 断言数 | 113 | **138–139** |
| 跨单可复现 | ✗ 硬编码单期数值 | ✓ 全部由数据驱动 |
| XIRR 合理性 | ✗ 无 | ✓ 区间断言（优先 −5%~15%、次级 −20%~80%） |
| 费用明细对平 | ✗ 不查 | ✓ 查 |
| 逐期分档 vs 清算报告 | ✗ 不查 | ✓ 查 |
| rebless 保护 | ✗ 直接定基线 | ✓ 先过 G3 才允许，且留痕 |
| 字段缺失 | 💥 KeyError 崩栈 | ✓ 前置契约检查，EXIT=2 + 缺失清单 |
| 诊断信息 | FAIL 只给描述 | ✓ FAIL/SKIP 分流 + 分组统计 + 残差量化 |

## 四、凭什么说「100% 复刻」

**实测证据**（2026-10-28）：

1. 把 5 个输入文件复制到**全新目录**（不同盘符、不同层级），用 `build_single.py` 构建
   → 产物 SHA256 **与原始完全一致**（`7ca4f737…ce929`）。**路径无关**。
2. 构建过程不含时间戳、不含绝对路径、不读系统语言 → **确定性**。
3. 输出用 `newline=""` 写入，**不转换换行符** → Windows/Linux 产物一致。
4. 三级门禁把「一样」拆成可测量的三件事：
   - **G1 字节级**：文件哈希相等（最强，1 秒出结果）
   - **G2 语义级**：93 项逐节指纹（高度 ±3px、计数零容差、文案逐行 diff）
   - **G3 数值级**：113 项断言，其中 23 条**独立复算**
5. 六个冗余保护（见 `references/17` 第八节）让「跑错」当场暴露，而不是悄悄产出错的报告。

> 唯一的不可控项是**系统字体**（微软雅黑 UI）。缺字体会导致高度漂移 1–2px，G2 会直接报出来。
