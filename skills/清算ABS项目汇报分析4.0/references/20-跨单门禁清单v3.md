> 相对 2.0 的 113 项，净增 **25 条**。新增的每一条都对应一次**真实放过错误**的事故，

### 已知的真实 SKIP（不是缺陷，是披露缺失）

| 单 | 跳过项 | 原因 |
|---|---|---|
| 惠元 2021 年第三期（技能自带样例） | 恒等式①②、首个支付日、XNPV 折现率 | payload 为旧版取数器产物，缺 `liab_at_begin_total` / `liab_at_end_total` / `first_pay_date` / `meta.rf` |
| 惠元 2023 年第四期 | 日期序、首个支付日 > 发行日 | 说明书的日期是**域字段**，文本层只剩「交付日 年 月 日」，`first_pay_date` 与 `legal_maturity` 取不到（`issue_date` 已由成立公告兜底拿到 2023-09-20） |

这两种都**不影响报告结论**：恒等式①②用于清算勾稽，日期序用于合理性，核心指标
（证券化率 / 回收率 / 处置费率 / XIRR）都不依赖它们。如实报 SKIP 比伪造一个值好——
伪造会让门禁变成自证。

## 二、★v3 新增：复算组 10 条

### 1. 逐期分档本金合计 ＝ 清算报告兑付额

```python
abs(sum(p["sen_principal"]) - L["sen_principal_paid"]) < 1.0
abs(sum(p["sub_principal"]) - L["sub_principal_paid"]) < 1.0
```

**放过的事故**：2022 年第四期，逐期优先档本金合计 3.861 亿，清算报告 3.170 亿，**多算 6,910 万**，
次级档 XIRR 因此虚高到 **218%**，门禁全部通过。

**根因**：分层结构表在优先档清零的那一期，该格是空的，整行只剩次级档一个数。按位置取值
（`lay[0]`）就把次级档余额当成了优先档余额，下一期再"清零"时就记成一笔巨额兑付。

**为什么 2.0 抓不住**：它只校验了清算报告一侧的数字（`sen_principal_paid == issue`），
从没校验"逐期加总"与"清算报告"是否一致。两个都"自洽"，但互相对不上。

**修法**：数据源改为兑付表「本息兑付后剩余本金值（元/百元面额）」× 发行额 ÷ 100，
每期必有、无歧义。断言守住这条一致关系。

### 2. 费用明细合计（＋未单列手续费）＝ 信托费用支出合计

```python
abs(sum(fee_detail.values()) + (misc_fee or 0) - fees_total) < 0.02
```

**放过的事故**：2022 年第六期、2023 年第七期各漏「受托机构报酬」**25 万元**，门禁通过。

**根因**：OCR 在科目名中间换行（`受托\n机构报酬`），正则按整名匹配不到，该科目被静默丢弃。
明细少一项，合计也就少了，但 2.0 从没比对过"明细合计 vs 披露合计"。

**修法**：匹配前先 `ns()` 去空白；断言强制对平。

### 3–4. 费用明细含核心科目「处置费」「贷款服务费」

**根因**：这两项是分配顺序 (d) 与 (b) 的前提，缺了整个"处置费率"没有来源。
单独检查它们是第二道闸——即使合计凑巧对上，也不能接受核心科目缺失。

### 5. 逐期累计回收单调不减

**抓什么**：负回收、期间错位、两期数据串列。累计序列一旦回退，说明某期 `in_total` 取错。

### 6–8. 预测现金流三连（合计对平 / 逐期衔接 / 末期归零）

```python
abs(sum(x[2] for x in fc) - exp_recovery_zz) < 1e4       # 合计对平
abs(fc[i][1] - fc[i-1][3]) <= 1.0                        # 期初 = 上期期末
abs(fc[-1][3]) < 1.0                                     # 末期期末 = 0
```

**放过的事故**：2024 年第一期，预测现金流 36 期合计 60,825.81 万，中债预计回收 53,995.98 万，
**多 6,830 万（一整期）**。原因是说明书把长表分页时，下一页顶部**整行重复**了上一页首行。

另有 2022 年第四期：末期"期末本息余额"写作 `-` 表示 0，被当成非数字丢弃，少一期 388 万。

**修法**：只去重「与首行完全相同」的行（按任意重复去重会误删真实数据）；`-` 按 0 处理。
断言三条一起守：合计对平抓"多算"，衔接抓"错位"，末期归零抓"少算末段"。

### 9–10. 清仓回购：已发生则起算日必存在 / 价款 ≤ 累计回收

**关键点：判据必须用 `occurred`，不能用 `price > 0`。**

实测 2022 四期、2024 一期都是 `occurred: true` 但 `price: 0.0`（回购已发生、价款为零，
剩余资产已无价值）。用 `price` 判断会把这类单误判成"无回购"，从而**根本不触发检查**——
2024 一期正是因通知日只披露到「月」（"2025 年 2 月"）导致整个回购块解析失败。

## 三、★v3 新增：合理性组 18 条（2.0 完全没有）

这一组不依赖任何单期特征，只用"任何清算ABS都该成立"的边界挡住明显错数。
**最容易被污染的就是 XIRR**——它表面永远"像个收益率"，错到 218% 也不刺眼。

| 2 | 次级档 XIRR | −20% ~ 80% | 次级实测 13.2%–74.6%，留足两端余量 |

| 6–7 | 优先档余额末期归零、单调不增 | — | 本金全额兑付的直接证据 |

## 四、★容差设计原则（v3 最重要的方法论）

**容差按披露精度设定，不按"看起来严格"设定。**

2.0 的教训：把容差设成 `1e-9`、`1 万元`这类"看起来很严"的数字，结果**误报一堆**，
然后为了过而一路放宽——最后失去了敏感性，这才是真正的风险。

### 三条实测

| 断言 | 2.0 式容差 | 实际残差 | 正确容差 | 依据 |
|---|---|---|---|---|
| 回采校验 | 1 万元 | 157,923 元（211ppm） | `max(1e4, 入池 × 5e-5 × 1.2)` | 回收率只披露到 4 位小数，40.87 亿 × 5e-5 ≈ 20.4 万是**数学必然** |
| 次级档占比 | 1e-9 | 4e-5（0.1509 vs 0.150943） | `5e-5` | 字段四舍五入到 4 位小数 |
| 达成率 | 1e-9 | 1.93bp（91.1407% vs 91.1599%） | `5e-4` + 要求正文出现金额口径值 | metrics 残留旧口径（18.28% 反推） |

### 结论

- 比例类字段在披露文件里**都是四舍五入值**，反算必然带舍入误差。容差＝该字段精度的理论上限。
- 这样设定**不会漏掉真错**：真错都是 bp 级或万元级以上（2022 四期分档差 6,910 万、
  2022 六期漏 25 万），该容差仍是数量级的差距。
- 每条带容差的断言都必须**把残差打印出来**。看不见的容差等于没有容差。

### 已经定好的几个容差，不要随手改

| 断言 | 容差 | 理由 |
|---|---|---|
| 资金平衡 | 1 万元 | 各单清算开始日是否有额外权益注入不同（2022 五期 1,000 元）；1 万元相对 3 亿级回收约 0.0003% |
| 逐期回收累计 | 100 元 | 两侧各自四舍五入，2023 二期差 11.47 元 / 7.5 亿 |
| 信托账户流出 ≥ 资产池流出 | 负向 0.1% 回收额 | 正常口径差 0.03% 量级；真错会到 5%（2022 五期 −20,397,876） |
| 跨期结转差额 | < 当期流入 15% | 账户间调拨，非记账差错 |
| 分档本金合计 | 1 元 | 金额对金额，精确 |
| 费用明细合计 | 0.02 元 | 金额对金额，精确 |

> ⚠ **反例警示**：曾把「信托账户流出 ≥ 资产池流出」改成绝对值判断
> `abs(gap) <= 0.1%回收`，结果 6 单全挂——因为这个不等式**本来就是有方向的**
> （信托账户流出含账户间调拨，恒大于资产池流出）。容差可以放宽，**方向不能丢**。

## 五、★流程门禁（比断言更重要的漏洞）

### 1. rebless 前必须先过 G3

2.0 的 `--rebless` 直接把当前产物定为黄金基线。**若产物本身有错，错误就被固化成"正确"**，
之后 G1/G2 永远通过，门禁等于废掉。

3.0 改为：

```bash
python repro_gate.py --rebless            # 先跑 G3，全过才重设
python repro_gate.py --rebless --force --why "原因"   # 强制跳过（须用户同意）
```

**实测验证**：把第三期产物的 `91.14%` 改成 `99.99%` 后尝试 rebless →

```
✗ [复算] 达成率 = 累计回收 ÷ 中债预计回收（金额口径，容差 5bp）
        金额口径 91.1407% vs metrics 91.1599%（差 1.93bp）
❌ G3 未通过 → 拒绝重设基线。   EXIT=1
```

### 2. 基线变更留痕

每次 rebless 把旧 sha256 追加到 `golden/history.tsv`（时间 / 旧哈希 / 原因），可回溯
"哪天为什么变"。没有留痕的基线变更一律视为回归。

### 3. 门禁未过绝不改基线，且返回非零

项目早期 `53_pipeline.py` 曾**无条件**在门禁前执行"建立基线"，等于每次自己跟自己比，
G1 形同虚设，曾因此放过 2022 四期的 4 项 FAIL。

现行规则：
- 无基线 → 不自动建，提示「首次交付需 --rebless」
- 有基线 → 直接比对
- 门禁不过 → 打印「不得交付」并 `return 1`
- 重建脚本（`57_rebuild_verify.py`）→ 重建 → 只跑 G3 → G3 全过才 rebless → 复验 EXIT=0

### 4. 改了解析器必须全量回归

15 单累计回归 4 轮。每改一次取数/组装/断言，**所有已交付单都要重跑**。
单点验证通过不代表没有回归——2021 一期就曾被"只改 2024 一期"的修补破坏过。

## 六、怎么在别的单子上用

```bash
# 1) 体检（环境 + 输入 + 字段契约）

# 2) 门禁（产物已存在）
python scripts/single/repro_gate.py --html /path/to/report.html

    --assets /path/to/02_提取数据 \

```

`--assets` 是 v3 新增：便于**不污染技能目录**地复核任意单子，也便于批量对比。

## 七、断言自查清单（写新断言时对照）

1. 这条断言**抓的是什么具体错**？说不出具体错就别写。
2. 它是"独立重算"还是"抄 metrics"？抄 metrics 的不算校验，只是同源自洽检查。
3. 容差依据是什么？是披露精度、还是"我希望它过"？
4. 残差有没有打印出来？
5. 字段缺失时是 FAIL 还是 SKIP？判据清楚吗？
6. 有没有**方向性**被我做成绝对值了？（`≥` 不能写成 `abs ≤`）
7. 注入一个错，它真的会红吗？

## 八、★4.0 新增的 3 条断言（兴业 10 单实践产出）

| # | 断言 | 抓什么错 | 容差依据 |
|---|---|---|---|
| A1 | **{档位} XIRR 可由现金流复算** | 两套现金流并存：卡片按逐期支付日算、折现表把收益合并挂清算日 | 1bp。两条路径若同源，反算必然精确相等；1bp 只留二分法收敛余量 |
| A2 | **清仓回购已发生则起算日必存在**（改写） | 只披露通知书日、不单列起算日；以及「全文泛指提及」被误判为已发生 | 存在性判定用 `occurred`，**不能用 `price > 0`**（「已发生但价款 0」是真实情形） |
| A3 | **次级档固定资金成本 ≈ 发行额 × 合同利率 × 天数/365** | 固资 A/B 体例判错 | 折年化应是**整十/整百**百分数（实测 10.00%）。非整数即拆错 |

### A1 的实现要点

```python
_FL = (M.get("flows") or {})
for _side, _mkey, _nm in (("sen", "sen_xirr", "优先档"), ("sub", "sub_xirr", "次级档")):
    from datetime import date as _d          # ★ 必须写在循环体内或模块顶部
    _raw = _FL.get(_side) or []
    if not _raw or M.get(_mkey) is None:
        skip("复算", f"★v3 {_nm} XIRR 可由现金流复算（口径同一）", "flows 缺失")
        continue
    _cf = [(_d(*map(int, x["date"].split("-"))), float(x["cf"])) for x in _raw]
    chk("复算", f"★v3 {_nm} XIRR 可由现金流复算（口径同一）",
        abs(_xirr_of(_cf) - M[_mkey]) * 1e4 <= 1.0,
        f'flows 反算 {_xirr_of(_cf)*100:.2f}% vs 卡片 {M[_mkey]*100:.2f}%')
```

> 踩坑：把 `from datetime import date as _d` 写在 `def` 里、在模块级用 `_d`，
> 会 `NameError: name '_d' is not defined`，而构建脚本只显示「断言 ?」——整块静默失效。
> **改完断言必须直接跑一次 `verify_single.py` 看有没有崩栈**，不能只看批量脚本的汇总行。

### A2 的三种情形（必须分开）

| 情形 | 处理 | 实例 |
|---|---|---|
| 披露金额 | 提取 + 单列自然清收回收率 | 兴瑞2023七期 322,969.87（OCR 写作 `322.969.87`） |
| 只披露事实与日期 | 记「已回购、金额未披露」，**不倒推** | 兴瑞2021二期、2024三期 |
| 全文仅泛指提及 | **不判为已发生** | 兴瑞2021一期（「含提前终止时清仓回购资产」） |

第三种若误判，会记出一个没有任何日期的空回购块，把 A2 逼成 FAIL。

### 4.0 断言总量

| 行 | 单数 | 断言/单 | FAIL |
|---|---|---|---|
| 惠元（中信） | 35 | 141 | 0 |
| 和萃（招商） | 19 | 136–142 | 0 |
| 建鑫（建设） | 24 | 138–142 | 0 |

> 断言条数因单而异是**设计预期**：可选字段缺失的走 SKIP，条数就少几条。
> **判断标准只有一个：FAIL = 0。**
