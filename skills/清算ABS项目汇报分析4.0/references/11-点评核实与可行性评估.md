# 11 · 点评核实与可行性评估

> 用户的工作方式：**把一份（AI 或人工）点评/规格书贴过来，先问「可行吗 / 是否中肯」，确认后才动手。**
> 本文是标准应答方法。**不要照单全收，也不要直接开干。**

## 一、第一步永远是：核实，不是表态

拿到点评后 **逐条对照真实数据/产物**，把每条判成四档：

| 判定 | 含义 | 处理 |
|---|---|---|
| ✅ **完全成立** | 实测确实如此 | 列入修改点 |
| ⚠️ **部分成立** | 方向对但细节有误 | 修正后列入 |
| ❌ **不成立** | 旧版信息 / 误读 / 字段不存在 | **明确说明为什么不做** |
| 🆕 **更新版本已改** | 点评针对旧版 | 附实测证据说明已解决 |

**实测比例**：本项目多轮点评里约 **20% 不成立或已过时**。
典型：
- 「总览有账户配平 ✓」→ v4 已删，渲染后 0 处
- 「总览按银行分组但实际平铺」→ 事实已按品种分组
- 「预计回收率分布单位是笔数」→ 实际按余额，且每桶两口径都有
- 「预测 XIRR vs 实际」→ **该字段根本不存在**
- 「次级档断点在第 9/10 期」→ 该单只有 8 期，且逐期 `begin[i+1]==end[i]` 无断点

## 二、核实要产出「带数字的证据」

不要写「已核实，正确」。要写：

```
橙益2024年第八期实测：
  alloc.cum 优先档本金 = 74,000,000（7,400万）
  alloc2   优先档本金 = 54,000,000（5,400万）  ← 分档兑付表口径
  发行规模 = 5,400 + 2,000 = 7,400万
  → 点评说「瀑布写了发行规模」✅ 成立
```

## 三、可行性评估的结构（用户认可的模板）

```markdown
## 总评
可行 / 部分可行 / 不可行，一句话结论 + 关键阻碍

## 一、逐条判定表
| # | 要求 | 判定 | 实测依据 |

## 二、⚠️ 数据硬缺口 / 逻辑冲突（最重要）
- 字段不存在 → 列出实测可得率
- 公式有歧义 → 给出两种算法结果对比
- 要求之间互相矛盾 → 明确指出

## 三、需要你拍板的 N 件事
每个给 2–3 个方案 + 代价

## 四、结论
「只要确认 X，就可以开干」
```

## 四、最容易踩的三类「规格书陷阱」

### 陷阱 1 · 规格书默认了不存在的字段
例：「哑铃图左端 = 预测 XIRR」
→ 实测 `*xirr*forecast*` 等 9 种命名全库 **0 命中**。
→ **必须降级方案**：改「定价假设（票面/约定率）→ 实际兑现（XIRR）」，并改标题、加脚注。

### 陷阱 2 · 规格书给了有歧义的公式
例：「剩余次级本金取**当期先兑付本金后**的余额」（期末口径）
→ 实测：中誉至诚2023第四期 期末口径 **21.47%**、期初口径 **12.00%**，说明书约定率 **12%**。
→ **期初口径才对**。直接用规格书公式会产出错误数字。
→ 处理：**先算两种口径对比给用户看**，再决定；或建议不做该项（v11 最终取消倒算）。

### 陷阱 3 · 规格书内部自相矛盾
例：
- B.1「左端＝剔除已单列超额后的倒算率」
- B.5「禁止在未拆分额>0 时标『已剔除超额』」
→ 建鑫2022第一期未拆分额 164 万 > 0 → 两条打架。
→ 处理：**明确指出**，给折中（该单画全口径空心点 + 「口径不完整」徽章）。

## 五、图表设计的可行性判断（常见误判）

| 规格书要求 | 实测风险 | 判断方法 |
|---|---|---|
| 哑铃图比较两个相近指标 | 差异小时退化成点阵 | 先算**差异分布**（min/p25/中位/p75/max）；若极差 < 坐标轴量程的 5%，改「排序条 + 叠点」 |
| 两个指标画同一坐标轴 | 量纲不同 | 检查量级：如「票面 2%–3.2%」vs「XIRR 8%–28%」不能同轴 |
| 帕累托看费用集中度 | 被证券本金主导 | 检查科目构成；含本金则**只对费用类做** |
| Top10 + 其他 | 其他占比过大 | 算「其他」合计占比；>30% 要考虑 Top15 |
| 给 37 类画圆环 | 完全不可读 | 类别 >15 一律 TopN 水平条 |

## 六、回复语气

- **直接说结论**，不要「这是一个好问题」
- **先认自己的错**，再指出对方的错（本项目我承认过：单位修复只修了 donut 没修 hbar；断言方法错 3 次）
- **不吹**：实测不满意的就说「仍有 25–30% 留白」
- **给选择**：不要替用户拍板有重大代价的事

## 七、确认后开干的动作

1. 先立 **修改点清单**（序号/位置/原问题/改法/影响/验收点）
2. 分派 agent（大改）或自己做（小改）
3. 组装 → 断言 → 出图
4. 回报时**逐条对照原点评**（哪条做了、哪条没做、为什么）

## 八、用户会追问的问题（提前准备）

| 追问 | 应答要点 |
|---|---|
| 「是否中肯？」 | 给判定表 + 命中率（如「7/10」） |
| 「有没有遗漏？」 | 指出点评**没覆盖**的问题（如点评没提 hbar 量级） |
| 「可行吗？」 | 给可行度百分比 + 硬缺口 + 拍板项 |
| 「别臆造」 | 明示「字段不存在就不画」 |
| 「不要放C盘」 | 交付物一律 E 盘项目目录 |
| 「每次重命名」 | v2…v11，不覆盖 |
